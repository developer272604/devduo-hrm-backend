# HRM MASTER SPECIFICATION

## PHASE 2 — CORE PEOPLE & EMPLOYEE MANAGEMENT

Continue from the completed Phase 1 foundation.

The product is:

- Multi-country from Day 1
- Multi-tenant SaaS
- Enterprise-capable
- Designed to compete with leading HRMS platforms such as Keka
- API-first
- Permission-aware
- Workflow-ready
- Audit-first
- Mobile-responsive

Do NOT rebuild Phase 1 components.

Reuse:

- Authentication
- Tenant isolation
- RBAC
- Organization structures
- Design system
- Application shell
- My Work
- Notifications
- Audit framework
- Settings framework
- API client
- Error handling
- Reusable forms/tables/modals/drawers

Do NOT start:

- Payroll processing
- Full attendance processing
- Recruitment/ATS
- Performance reviews
- Learning
- Expense management
- Advanced analytics

However, architecture created in this phase MUST support these future modules.

==================================================
1. PEOPLE DOMAIN ARCHITECTURE
==================================================

Create a dedicated People domain.

Employee must NOT be tightly coupled to User.

An Employee represents a person/employment record.

A User represents authentication/access.

Support:

- employee without login
- employee with login
- pre-joiner
- active employee
- inactive employee
- separated employee
- contractor
- intern
- consultant
- temporary worker
- rehired employee
- multiple employment records over time

Use UUID/public-safe identifiers where appropriate.

Do not expose sequential internal database IDs unnecessarily.

Every tenant-owned record MUST enforce tenant isolation.
